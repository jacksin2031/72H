## P2.4 — 官方災害資訊引擎

### A. 官方產品與事件契約

初次範圍為現有 JMA「震源・震度に関する情報」與 VTSE41 海嘯警報產品的生命週期。
依官方產品說明核實電文識別、修訂次序、取消對象及區域代碼；不擅自以所有產品共用的規則排序。
以官方 schema、代碼表及樣本建立有版本的測試資料。公開 XML PULL 不作為低延遲緊急地震速報保證。

新增官方電文 envelope，保留以下語意，再投影至既有 `DisasterEvent`／`Evidence`：

- 官方機關、來源 URL、產品類別、原始電文 hash、parser／代碼表版本。
- 官方 event ID、產品內報次／serial、獨立 report ID、修訂與取代關係。
- 發表、災害發生、產品適用時間及本機接收時間；不存在的時間保留未知，不用下載時間填補。
- 官方目標區域代碼與範圍，以及警報級別、震度與其觀測粒度。
- 電文操作（發表／訂正／取消）、區域警報狀態（生效／變更／解除）、有效性及失效原因。

欄位名稱及必填性須經 A 的官方產品核實後定稿；以上是語意需求，不是已上線的新 schema。
現有 `DisasterEvent.occurred_at` 必填，不能將無發生時間的解除／取消硬塞成假時間；
應先用獨立 envelope 表達控制事件，再決定兼容投影或有版本的契約遷移，並保留舊 snapshot 讀取測試。

官方提供的有效時間與 Safety Core 的證據 TTL 必須分開。
現有官方災害證據 15 分鐘 TTL 是應用政策，**不是官方警報會於 15 分鐘後解除**。
重取相同電文不能延長其新鮮度。未知或過時代表不能核實當前狀態，不能推論災害已結束。

### B. 純函式生命週期 reducer

- 依已核實的產品規則建立 event group／revision key；不只依到達時間或 EventID 判斷修訂。
- 相同電文重送保持冪等；較舊電文不得恢復已取代或已取消的狀態。
- 訂正保留原文與歷史，明確取代錯誤證據，觸發相關計劃依賴失效。
- 電文 `取消` 與區域警報 `解除` 分開建模；取消錯誤報文不等於該區無海嘯警報。
- 不同地震／海嘯事件群互不清除；無法識別取消對象或相同識別出現矛盾內容時，隔離並保持 UNKNOWN／CONFLICT。
- 缺少識別、無效時間或未核實區域映射不能支持高風險行動。
- 失效後保留版本化計劃歷史，所有畫面同時停止呈現受影響的可執行指引。

### C. 有界擷取、持久化及重連

重用現有來源 allowlist、大小限制與輪詢，加入可恢復的 checkpoint、原始電文紀錄及去重索引。
採用條件請求及有界重試；補抓時按官方長期 feed 與產品規則核實是否有缺口，
不能把近期 feed 為空當成無警報，亦不能只靠目前「最多五份 detail」假設已補齊。
checkpoint 只在資料驗證並成功保存後前移。

明確分開來源連線健康、最新成功接收、最新官方發表及當前災害有效性。
服務重新啟動、離線 TTL 到期、補抓不完整及持久化失敗均有可測試狀態。
網絡回復先進入 RECONNECTING，逐一核實相關事件群，再交由 Safety Core 解除限制；
舊快照或單次成功下載不能直接宣稱 ONLINE_VERIFIED。

### D. 投影及驗收

API／UI 顯示來源、發表與更新時間、目標區域、資料年齡、生命週期、最後核實時間及限制。
使用既有證據 pipeline、依賴評估及版本化計劃，不引入按 replay 步數切換結果的捷徑。
LIVE 與 REPLAY 的來源、快照及狀態保持隔離。

必測序列：發表 → 後續更新 → 訂正 → 取消錯誤電文／區域解除 → 斷線 → 過時 → 重連補齊。
另測亂序、重複、同時兩個事件、相同識別不同內容、未支援產品、區域不明、來源逾限、
未完成補抓、重啟恢復及接收時間不能刷新 TTL。
有效性變更必須驅動真實 Safety Core 及 plan history；拒絕資料不能造成不安全的警報清除。

**首個有界實作包：A＋B，優先補地震訂正／取消及統一生命週期契約。**
完成後才串接 C／D。P2.4 通過前，不以新增全國災害着色宣稱當前狀態已核實。

## P2.5 — 多圖層災害地圖

每個圖層保留自己的來源、產品／資料版本、適用時間、核實狀態及範圍：

1. **震度觀測**：呈現官方實際提供的測站／地域粒度；現有都道府縣最大震度不能塗成每個地點的實測震度。
2. **海嘯警報**：以官方預報區代碼連接有版本的官方幾何；不假設預報區等於都道府縣。
3. **自治體浸水預測**：保留情境條件、深度級別、公布日期、CRS、精度及獨立研究覆蓋範圍。
4. **資料來源與覆蓋**：使用者可以看到來源、時間與「未判定」原因。

靜態浸水假設、當前警報、實測震度與現有 P／S 估算波前，必須使用不同圖例及文字。
核實資料本身不代表核實當前安全。多邊形之外若沒有獨立研究覆蓋證據，仍是未判定。
不得用沒有着色推論無風險，亦不得用道路底圖推論道路暢通。
舊警報離線時保留清楚的資料年齡與失效狀態；不繼續使用「當前已核實」樣式。

重用石卷 pilot，依分區 manifest／hash 逐步擴充；未完成地區保持未判定。
驗收包含代碼／幾何版本不一致、邊界位置、缺範圍、圖層衝突、離線／重連及手機圖例布局。

## P2.6 — 災害類別適用的避難地點

接入 GSI 指定緊急避難場所及指定避難所 GeoJSON，重用現有 CSV 的分類與角色模型。
先核實官方 GeoJSON schema，再測試相同來源紀錄的 CSV／GeoJSON 正規化一致性。
保留來源識別、自治體、更新資訊、角色及八類災害適用值；未提供與明確不適用不能混為一談。
按分區 pack 更新，避免把全國所有資料強制預快取到每部裝置。

「指定緊急避難場所」為避開特定災害的指定場所；「指定避難所」用途不同，不能互換。
地震／海嘯篩選只表示官方指定適用分類，不能顯示為「已證實安全」。
官方目錄未提供可靠更新時間時，顯示未知；擷取時間只證明何時取得資料。
GSI 公開目錄範圍亦不等於所有可能場所或當前開放情況。

另以具權責自治體的當前證據核實開放／關閉、對象、時間及必要限制。
開放狀態使用 OPEN／CLOSED／UNKNOWN 並有來源及 TTL；缺資料、過時或衝突回到 UNKNOWN。
缺開放 feed 不阻止顯示指定用途，但阻止把場所標為當前可用目的地。
即使 OPEN，仍須滿足 Safety Core 的災害適用、目的地與移動授權及路線依賴；不單獨授權移動。

驗收包含場所雙角色、八類分類、缺值、撤銷／更新紀錄、錯誤座標、GeoJSON 超限、
指定適用但已關閉、未知開放及「場所可用但路線未核實」案例。

## P2.7 — AI 行動解釋引擎

新增目標流程：

```text
官方證據 → 決定性核實與狀況更新 → Safety Core／決定性計劃
→ 已核實事實、限制及允許行動 envelope → Gemini／ADK 解釋
→ 輸出驗證與版本核對 → 呈現 → 持續監察
```

現有 `CandidatePlanner` 會在最後 Safety Core gating 前產生候選計劃；
這與本階段「AI 只負責解釋」的目標不同，不能宣稱現有流程已滿足新要求。
以使用者的新要求收窄行動流程中 AI 的權限；實作時同步更新 Safety Contract、Architecture
及候選 planner 的 LIVE／REPLAY 兼容測試，不靜默保留 AI 選擇行動的入口。

輸入只包含已批准的 fact／action／evidence ID、計劃版本、限制、有效期及語言。
精確 GPS 留在裝置，不傳給 AI；外部文字是資料，不是指令。
提供簡潔中文、日文及英文，說明現在做甚麼、為何、哪些仍未核實及何時需要重新核實。

輸出必須通過 schema、ID 白名單、證據綁定及計劃版本檢查。
目的地、行動、路線及安全狀態以決定性資料呈現，AI 不能新增或修改。
無法核對的自由文字不作為行動指令發布；不能只靠禁止詞或 prompt 當成安全驗證。
超時、無效輸出、缺證據及晚到的舊版本結果，使用已核實資料的固定多語模板。
解釋不能改變 Safety Core 決策、計劃 TTL 或移動授權。

保留真實 Gemini／ADK 執行與 Cloud Run runtime，不能以預錄文字冒充模型接入。
驗收包含三語一致性、提示注入、杜撰目的地／路線、遺漏限制、ID 不符、
訂正或取消後晚到的解釋、模型失敗及離線固定解釋。
